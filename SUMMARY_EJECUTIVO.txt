🔴 VULNERABILIDADES CRÍTICAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. ❌ BLE SIN CIFRADO
   └─ Credenciales WiFi + API Secret transmitidas en TEXTO PLANO
   └─ Cualquiera puede esnifar: SSID, contraseña, secret
   └─ Riesgo: Completa suplantación del dispositivo
   └─ Solución: Implementar BLE Encryption + Security Pairing

2. ❌ NVS SIN FLASH ENCRYPTION
   └─ Datos almacenados en flash del ESP32 sin cifrado
   └─ Con acceso físico: esptool.py read_flash → credenciales visibles
   └─ Riesgo: Compromiso total del dispositivo
   └─ Solución: Habilitar Flash Encryption (menuconfig)

3. ❌ TIMING ATTACK EN VALIDACIÓN DE DEVICE
   └─ Usando .equals() en lugar de timing-safe comparison
   └─ Atacante mide tiempo HTTP para adivinar API Secret carácter por carácter
   └─ Riesgo: Extracción de API Secret en ~5 minutos
   └─ Solución: MessageDigest.isEqual()

4. ❌ JWT SIN CLAIMS DE SEGURIDAD
   └─ Falta "jti" (JWT ID): Token reusable forever
   └─ Falta "type": Confusion attack (access usado como refresh)
   └─ Falta "aud" (audience): Token válido en múltiples APIs
   └─ Riesgo: Token leak = acceso indefinido
   └─ Solución: Agregar claims + validar tipo en cada endpoint

5. ❌ SIN RATE LIMITING EN API DE SENSORES
   └─ GET /api/v2/sensors/reading NO tiene rate limit
   └─ Atacante puede inundar: 10,000s lecturas/segundo
   └─ Riesgo: DoS + Inyección de datos fraudulentos
   └─ Solución: Implementar Bucket4j (100 req/min por device)

6. ❌ SIN CERTIFICATE PINNING EN HTTPS
   └─ ESP32 acepta CUALQUIER certificado válido de CA
   └─ MITM con cert de Let's Encrypt = Compromiso total
   └─ Riesgo: Interceptación de API Secret + datos
   └─ Solución: Pinear certificado del servidor en ESP32

7. ❌ SIN DEDUPLICATION EN SENSOR READINGS
   └─ Mismo reading puede insertarse múltiples veces
   └─ Atacante inyecta 100 lecturas duplicadas
   └─ Riesgo: Análisis e diagnósticos falsos
   └─ Solución: Agregar reading_id único + constraint UNIQUE


🟠 RIESGOS ALTOS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

• API Secret enviado por WiFi del usuario (potencialmente débil)
• JWT Secret en environment variable sin protección
• CORS permisivo para capacitor://localhost
• Sin CSRF protection en device linking
• Password authentication no validado
• Logs pueden contener PII (MAC address)


🎯 IMPACTO DE ATAQUES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ESCENARIO 1: Sniffer BLE cercano al dispositivo
  ┌─ Minuto 0: Dispositivo sincroniza por BLE
  ├─ Minuto 1: Atacante captura SSID + PASSWORD + API_SECRET en texto plano
  ├─ Minuto 2: Atacante se conecta a la WiFi del usuario
  └─ Minuto 3: Atacante suplanta el dispositivo completamente

ESCENARIO 2: Timing attack en API
  ┌─ Atacante obtiene macAddress de un dispositivo (publico)
  ├─ Usa timing de respuesta HTTP para deducir API Secret
  │  ("aaaaaaa0" vs "aaaaaaa1" → timing diferente = correcto)
  ├─ ~5 minutos: Extrae API Secret completo
  └─ Resultado: Acceso indefinido con datos fraudulentos

ESCENARIO 3: MITM con certificate hijacking
  ┌─ Atacante con acceso a ISP o red corporativa
  ├─ Intercepta conexión HTTPS del ESP32
  ├─ Presenta su propio certificado (CA válida comprometida)
  ├─ ESP32 acepta porque no hay certificate pinning
  └─ Intercepta API Secret + datos de sensor completos
